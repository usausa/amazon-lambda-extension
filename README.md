# AmazonLambdaExtension

English | [日本語](README.ja.md)

Source Generator for AWS Lambda HTTP API / Event handlers, inspired by [Amazon.Lambda.Annotations](https://github.com/aws/aws-lambda-dotnet/blob/master/Libraries/src/Amazon.Lambda.Annotations/README.md).

## What is this?

AmazonLambdaExtension is a library that uses .NET Source Generators to auto-generate boilerplate code for AWS Lambda functions.
It lets you declaratively describe parameter binding, the filter pipeline, and DI integration for HTTP API (API Gateway v2).

## Features

- **Dependency Injection** — Just declare a DI container with the `[ServiceResolver]` attribute and constructor arguments are resolved automatically.
- **Parameter binding** — `[FromRoute]` / `[FromQuery]` / `[FromHeader]` / `[FromBody]` / `[FromServices]` / `[FromAuthorizer]` / `[FromCookie]` / `ClaimsPrincipal`
- **HTTP results** — Status-code-aware responses via `IHttpResult` / `HttpResults`.
- **Authorizer** — Lambda authorizer generation via `[HttpApiAuthorizer]`.
- **Filter pipeline** — Chain multiple classes implementing `ILambdaFilter` with `[Filter<T>(Order = N)]`.
- **AOT compatible** — Zero AOT warnings with `IsAotCompatible=true` and `JsonSerializerContext`-based JSON serialization.
- **Native AOT entry point** — `[assembly: LambdaEntryPoint]` generates `Main` that runs the handler selected by `_HANDLER`.
- **Event handler** — Handle non-HTTP events such as SQS with `[Event]`.

## Installation

```xml
<ItemGroup>
  <PackageReference Include="AmazonLambdaExtension" Version="x.x.x" />
</ItemGroup>
```

The package includes the Source Generator.

## Basic Usage

### 1. Declare a Function class

```csharp
[Lambda]
[ServiceResolver(typeof(ServiceResolver))]
public partial class CrudFunctions
{
    private readonly DataService data;

    public CrudFunctions(DataService data)
    {
        this.data = data;
    }

    [HttpApi(LambdaHttpMethod.Get, "/items/{id}")]
    public async ValueTask<IHttpResult> GetItem(
        [FromRoute] string id,
        [FromQuery] int page,
        ILambdaContext context)
    {
        var item = await data.GetAsync(id, page);
        return item is null ? HttpResults.NotFound() : HttpResults.Ok(item);
    }

    [HttpApi(LambdaHttpMethod.Post, "/items")]
    public async ValueTask<IHttpResult> CreateItem([FromBody] CreateItemInput input)
    {
        var created = await data.CreateAsync(input);
        return HttpResults.Created($"/items/{created.Id}", created);
    }
}
```

An HTTP handler (`[HttpApi]` / `[FunctionUrl]`) may return any of the following:

| Return value | Behavior |
|:-----|:-----|
| `IHttpResult` / `HttpResult` (via `HttpResults.*`) | Converted to `APIGatewayHttpApiV2ProxyResponse` |
| `APIGatewayHttpApiV2ProxyResponse` | Returned as-is |
| Any other type (POCO) | Wrapped into a `200 OK` JSON response (equivalent to `HttpResults.Ok(value)`) |
| No return value (`void` / `Task` / `ValueTask`) | `200 OK` with no body |

`Task<T>` / `ValueTask<T>` wrappers and synchronous returns are all supported.

Throw `ApiException` to short-circuit with a specific status code (the message becomes the body):

```csharp
throw new ApiException(404, $"Item '{id}' not found.");
```

### 2. Implement the ServiceResolver

The Source Generator calls `ServiceResolver.ConfigureServices()` to build the DI container.

```csharp
public static class ServiceResolver
{
    public static IServiceCollection ConfigureServices()
    {
        var services = new ServiceCollection();

        // Lambda serializer (AOT-compatible — uses JsonSerializable source generation)
        services.AddSingleton<ILambdaSerializer>(
            new SourceGeneratorLambdaJsonSerializer<AppJsonContext>());

        // Body serializer (AOT-compatible — no reflection by passing a JsonSerializerContext)
        services.AddSingleton<IBodySerializer>(new JsonBodySerializer(AppJsonContext.Default));

        services.AddSingleton<DataService>();
        return services;
    }
}

[JsonSourceGenerationOptions(PropertyNamingPolicy = JsonKnownNamingPolicy.CamelCase)]
[JsonSerializable(typeof(CreateItemInput))]
[JsonSerializable(typeof(Item))]
[JsonSerializable(typeof(APIGatewayHttpApiV2ProxyResponse))]
internal sealed partial class AppJsonContext : JsonSerializerContext;
```

### 3. Configure the Lambda Handler

The handler name generated by the Source Generator is `{Namespace}.{ClassName}::{Method}_Handler`.
Lambda calls the handler named in the function configuration, so nothing needs to be registered in code. (Difference from AzureFunctionsExtension: Azure Functions finds functions through the Functions host, so the Source Generator there also generates the function metadata for the host.)

```yaml
"CrudGet":
  Type: AWS::Serverless::Function
  Properties:
    Handler: "MyApp::MyApp.CrudFunctions::GetItem_Handler"
```

## Parameter Binding

| Attribute | Binds from | HTTP API | Event |
|:-----|:-----------|:--------:|:-----:|
| `[FromRoute]` | Path parameter | ✅ | |
| `[FromQuery]` | Query string | ✅ | |
| `[FromHeader("name")]` | HTTP header | ✅ | |
| `[FromBody]` | Request body (JSON) | ✅ | |
| `[FromServices]` / `[FromServices("key")]` | DI container | ✅ | ✅ |
| `[FromAuthorizer("key")]` | Lambda authorizer context | ✅ | |
| `[FromCookie("name")]` | Cookie | ✅ | |
| `ClaimsPrincipal` (no attribute) | JWT authorizer claims | ✅ | |

- **Optional parameters** — `[FromQuery]` / `[FromRoute]` / `[FromHeader]` parameters with a default value (e.g. `[FromQuery] int page = 1`, `[FromQuery] Mode mode = Mode.Advanced`) bind that default when the value is missing, instead of returning 400. Default literals are emitted with invariant culture.
- Parameters with `[FromBody]` are automatically validated with DataAnnotations; a 400 is returned on failure. Invalid JSON returns `400 Invalid request body.`, and a non-nullable body type returns `400 Request body is required.` when the body is null/empty. Declaring the body type as nullable (`T?`) allows a null body.
- `[FromBody]` works without a `ServiceResolver`. When none is specified, the default `JsonBodySerializer.Default` and `DataAnnotationsRequestValidator` implementations are used.
- The body of an HTTP API request is a string in the event, so `IBodySerializer` reads and writes strings. Difference from AzureFunctionsExtension: Azure Functions passes the body as a stream, so the serializer there reads it asynchronously (`DeserializeAsync`).
- A `[ServiceResolver]` is required when using `[FromServices]`.
- `[FromServices("key")]` resolves a keyed service (`GetRequiredKeyedService`); without a key it resolves the default service (`GetRequiredService`).
- `[FromAuthorizer("key")]` reads the context returned by the Lambda authorizer (`requestContext.authorizer.lambda`). String, number and boolean values are converted to the parameter type; arrays are not supported.
- `[FromCookie("name")]` reads a cookie from the `cookies` array of the payload v2 (HTTP API does not put cookies in the headers) with the same rules as ASP.NET Core (see [Claims and Cookies](#claims-and-cookies)). It can be used in `[HttpApi]` and `[FunctionUrl]` handlers.
- `[FromCookie]` converts the value like `[FromQuery]`; a missing value binds the default value (or `null`), and arrays are not supported.
- **DI lifecycle**: The handler instance itself is a singleton (created once on cold start and reused across the execution environment). For dependencies that need `Scoped`/`Transient` lifetimes, receive them via **`[FromServices]` (a method parameter) or filters** (resolved from, and disposed with, a per-invocation DI scope). Dependencies injected into the handler's constructor are effectively singletons (to avoid captive dependencies). Difference from AzureFunctionsExtension: the function class there is created for each invocation, so its constructor dependencies come from the scope of the invocation.
- The only binding attribute that can be used explicitly in an `[Event]` handler is `[FromServices]`.
- An `[Event]` handler must declare exactly one payload (event body) parameter (zero or multiple is an error).
- `ILambdaContext` can be added as a parameter anywhere (no binding attribute needed).
- `CancellationToken` can be added as a parameter anywhere as well (see [Cancellation](#cancellation)).
- `ClaimsPrincipal` can be added as a parameter in `[HttpApi]` and `[FunctionUrl]` handlers (see [Claims and Cookies](#claims-and-cookies)).
- A `[Lambda]` class must be a top-level, non-generic, non-`abstract` `partial class` (generic types, nested types, records, and `abstract` are not supported; `struct`/`record struct` cannot carry `[Lambda]` at all). Filters likewise cannot be `abstract` without a `[ServiceResolver]`.
- `ConfigureServices()` of `[ServiceResolver]` only needs to be a `static` method reachable from the generated code (inside the Lambda class) — `internal` within the same assembly is fine. Likewise, the parameterless constructor of the handler/filter (when there is no `[ServiceResolver]`) is judged by "reachability."
- Handler names must be unique within a class (overloads with the same name are not supported).

### Claims and Cookies

Receive the caller as a `ClaimsPrincipal` parameter (no attribute), as in ASP.NET Core minimal APIs.

```csharp
[HttpApi(LambdaHttpMethod.Get, "/me")]
public IHttpResult GetMe(ClaimsPrincipal user, [FromCookie("theme")] string? theme)
    => user.Identity?.IsAuthenticated == true
        ? HttpResults.Ok(new { id = user.FindFirst("sub")?.Value, admin = user.IsInRole("admin"), theme })
        : HttpResults.Unauthorized();
```

- In `[HttpApi]` handlers, the `ClaimsPrincipal` is created from the claims validated by the HTTP API JWT authorizer (`requestContext.authorizer.jwt.claims`). API Gateway passes every claim as a string: a value in `[ ]` (an array, such as `[admin user]`) is split by spaces into claims with the same name, a `map[...]` value (an object) is not split, and `[]` adds no claim.
- `Identity.Name` and `IsInRole` use the `name` and `role` claims by default. To use other claims, register `LambdaClaimsOptions` as a singleton in the `ServiceResolver`.

```csharp
services.AddSingleton(new LambdaClaimsOptions { NameClaimType = "preferred_username", RoleClaimType = "roles" });
```

- With claims, the identity is authenticated. As with ASP.NET Core's JwtBearer, its `AuthenticationType` is `AuthenticationTypes.Federation`, and the `Issuer` of each claim is the `iss` claim (or `LOCAL AUTHORITY`). Without claims (for example, without a JWT authorizer), the `ClaimsPrincipal` is empty and unauthenticated.
- Filters read and replace the caller with `LambdaInvocationContext.User`. It is created when first read, and the handler receives the replaced one. For example, a filter can set the `User` from its own authentication.
- In `[FunctionUrl]` handlers, the `ClaimsPrincipal` is `LambdaInvocationContext.User` with filters, or an unauthenticated one without filters (a Function URL has no JWT authorizer). It cannot be used in `[HttpApiAuthorizer]` and `[Event]` handlers (ALE0404).
- `[FromCookie]` reads cookies with the same rules as ASP.NET Core's `HttpRequest.Cookies`: names are case-insensitive, values are URL-decoded (`+` is kept), the last one wins for the same name, an empty value is ignored (an earlier value stays), an entry with a character that is not allowed (whitespace, `"`, `,`, `;`, `\`, or non-ASCII) or with a space before `=` is ignored, and a quoted value keeps its quotes.
- Difference from AzureFunctionsExtension: the `User` there is the one the app sets on `HttpContext.User` (for example, with JwtBearer). With JwtBearer, `MapInboundClaims = false` and the same `NameClaimType` / `RoleClaimType` give the same claims as here, except for the following, which come from the strings of API Gateway:
  - An array element containing a space is split here, because the separators are lost in the string (`["a b","c"]` arrives as `[a b c]`).
  - An object claim is the `map[...]` string here, and JSON there.
  - The `ValueType` of a claim is always `string` here.

### Binding Errors

By default, a binding or validation failure returns a `400` with a text message.
To return your own response (for example, RFC 9457 Problem Details), register an `IBindingErrorResultFactory` as a singleton in the `ServiceResolver` (other lifetimes are not supported).

```csharp
public sealed class BindingErrorResultFactory : IBindingErrorResultFactory
{
    public IHttpResult Create(BindingError bindingError) =>
        HttpResults.BadRequest(new ErrorResponse(bindingError.Kind.ToString(), bindingError.Name))
            .AddHeader("content-type", "application/problem+json");
}
```

```csharp
services.AddSingleton<IBindingErrorResultFactory, BindingErrorResultFactory>();
```

| `BindingError` | Description |
|:-----|:-----|
| `Kind` | `InvalidValue` (conversion failed), `InvalidBody` (invalid JSON), `MissingBody` (non-nullable body is null), `ValidationFailed` (`IRequestValidator` failed) |
| `Source` | `Route` / `Query` / `Header` / `Body` / `Authorizer` / `Cookie` |
| `Name` | Binding key (route / query / header / authorizer / cookie name), or the body parameter name |
| `ValidationResults` | Results of `IRequestValidator` (only for `ValidationFailed`) |

- The factory is used by HTTP API / Function URL handlers in a class with `[ServiceResolver]`. Without the registration, the response is the same text `400` as before.
- In `[HttpApiAuthorizer]` handlers, a binding failure returns `AuthorizerResults.Deny()`, because an authorizer cannot return a `400`. The factory is not used (see [Authorizer](#authorizer)).
- Exceptions thrown by handlers are not passed to the factory. Handle them in a filter (for example, an outermost error filter).
- With filters, parameters are bound inside the pipeline, so a failure response (`context.Result`) also passes through the outer filters. For example, an outermost error filter can add a request ID to it or write a log.
- `BindingError`, `BindingErrorKind`, and `BindingSource` have the same names as in AzureFunctionsExtension, which does not have `BindingSource.Authorizer`, so the numeric value of `Cookie` differs (5 here, 4 there). Compare them by name, or write them as strings (for example, with `JsonStringEnumConverter`).

## Filter Pipeline

Apply classes implementing `ILambdaFilter` to a class with `[Filter<T>(Order = N)]`.
They are chained in ascending `Order`, and you can write logic before and after `await next(ctx)`.

```csharp
public sealed class LoggingFilter : ILambdaFilter
{
    public async ValueTask InvokeAsync(LambdaInvocationContext context, LambdaFilterDelegate next)
    {
        var sw = Stopwatch.StartNew();
        await next(context);
        Console.WriteLine($"Elapsed: {sw.ElapsedMilliseconds}ms");
    }
}

public sealed class ApiKeyFilter : ILambdaFilter
{
    public ValueTask InvokeAsync(LambdaInvocationContext context, LambdaFilterDelegate next)
    {
        var req = context.GetRequestAs<APIGatewayHttpApiV2ProxyRequest>();
        if (!req.Headers.TryGetValue("x-api-key", out var key) || key != "expected")
        {
            context.Result = HttpResults.Unauthorized();
            return default;
        }
        return next(context);
    }
}

[Lambda]
[ServiceResolver(typeof(ServiceResolver))]
[Filter<LoggingFilter>(Order = 0)]
[Filter<ApiKeyFilter>(Order = 10)]
public partial class SecureFunctions
{
    [HttpApi(LambdaHttpMethod.Get, "/secure/items/{id}")]
    public ValueTask<HttpResult> GetItem([FromRoute] string id)
        => ValueTask.FromResult(HttpResults.Ok(new { id }));
}
```

### Assembly-level Filters

`[Filter<T>]` can also be applied to the assembly. It applies to every `[Lambda]` class in the assembly, so a common pipeline does not need to be repeated on each class.

```csharp
[assembly: Filter<ErrorFilter>(Order = 0)]
[assembly: Filter<LoggingFilter>(Order = 10)]
```

- Assembly-level and class-level filters are chained together in ascending `Order`. With the same `Order`, the assembly-level filter is outer.
- When the same filter type is applied to both the assembly and a class, it runs twice.
- Assembly-level filters apply to every handler in the assembly, including `[Event]` and `[HttpApiAuthorizer]` handlers. A filter for HTTP API requests should check the type of `context.Request` and pass other invocations through (`[HttpApi]` and `[FunctionUrl]` handlers receive `APIGatewayHttpApiV2ProxyRequest`).

```csharp
public sealed class ApiKeyFilter : ILambdaFilter
{
    public ValueTask InvokeAsync(LambdaInvocationContext context, LambdaFilterDelegate next)
    {
        if (context.Request is not APIGatewayHttpApiV2ProxyRequest request)
        {
            return next(context);
        }

        if (!request.Headers.TryGetValue("x-api-key", out var key) || (key != "expected"))
        {
            context.Result = HttpResults.Unauthorized();
            return default;
        }

        return next(context);
    }
}
```

- An `[HttpApiAuthorizer]` handler that takes `APIGatewayHttpApiV2ProxyRequest` cannot be told apart by this check. When the filter sets an `IHttpResult` for it, the invocation fails with `InvalidCastException`. Take `APIGatewayCustomAuthorizerV2Request` in authorizers (see [Authorizer](#authorizer)).

### Cancellation

Filters (`LambdaInvocationContext.CancellationToken`) and handlers (a `CancellationToken` parameter) receive a token that is canceled at the remaining time of the invocation minus a margin (500 ms by default), so that the work can stop before the function times out.

```csharp
[HttpApi(LambdaHttpMethod.Get, "/items")]
public async ValueTask<IHttpResult> List(CancellationToken cancellationToken)
    => HttpResults.Ok(await data.ListAsync(cancellationToken));
```

```csharp
services.AddSingleton(new LambdaCancellationOptions { Margin = TimeSpan.FromSeconds(1) });
```

- The token is created only when the class has filters or the handler takes a `CancellationToken`.
- When `ILambdaContext.RemainingTime` is zero (for example, a test context), the token is never canceled.
- Difference from AzureFunctionsExtension: the token there comes from the Functions host (for example, when the client disconnects), and a time limit (`FunctionCancellationOptions.Timeout`) is added only when it is registered. Lambda does not signal those but tells the remaining time of the invocation, so the token here is based on the remaining time and works by default.

## Authorizer

```csharp
[Lambda]
[ServiceResolver(typeof(ServiceResolver))]
public partial class CrudFunctions
{
    [HttpApi(LambdaHttpMethod.Post, "/items", Authorizer = nameof(Authorize))]
    public async ValueTask<IHttpResult> CreateItem(
        [FromBody] CreateItemInput input,
        [FromAuthorizer("role")] string role)
    {
        if (role != "admin") return HttpResults.Forbid();
        var created = await data.CreateAsync(input);
        return HttpResults.Created($"/items/{created.Id}", created);
    }

    [HttpApiAuthorizer(EnableSimpleResponses = true)]
    public async ValueTask<IAuthorizerResult> Authorize(
        APIGatewayCustomAuthorizerV2Request request,
        ILambdaContext context)
    {
        if (!request.Headers.TryGetValue("authorization", out var token))
            return AuthorizerResults.Deny();
        return AuthorizerResults.Allow()
            .WithPrincipalId("user-123")
            .WithContext("role", "admin");
    }
}
```

- When using `Authorizer = nameof(Authorize)`, the target must be a `[HttpApiAuthorizer]` method in the same class.
- Take the request as `APIGatewayCustomAuthorizerV2Request`, the payload of an HTTP API Lambda authorizer. Filters can then tell the authorizer apart from HTTP handlers (see [Assembly-level Filters](#assembly-level-filters)).
- When returning the IAM policy format with `EnableSimpleResponses = false`, receiving an `APIGatewayCustomAuthorizerV2Request` automatically populates `RouteArn`.
- When a parameter fails to bind (for example, `[FromQuery] int page` with `page=x`), the handler is not called, and `AuthorizerResults.Deny()` is returned, as when the handler throws an exception.
- `[FromBody]` cannot be used, because the request of a Lambda authorizer has no body (ALE0402).

## Event Handler

Use `[Event]` for non-HTTP events (such as SQS).

```csharp
[Lambda]
[ServiceResolver(typeof(ServiceResolver))]
public partial class QueueProcessor
{
    private readonly IProcessor processor;

    public QueueProcessor(IProcessor processor)
    {
        this.processor = processor;
    }

    [Event]
    public async ValueTask Handle(SQSEvent ev, ILambdaContext context)
    {
        foreach (var record in ev.Records)
        {
            await processor.HandleAsync(record.Body);
        }
    }
}
```

```csharp
[Lambda]
public partial class HealthCheck

    [FunctionUrl]
    public IHttpResult Ping()
```

## AOT Compatibility

`JsonBodySerializer` has two constructors.

| Constructor | AOT support | Use |
|:--------------|:--------:|:-----|
| `JsonBodySerializer(JsonSerializerContext)` | ✅ | Pass a context generated by `[JsonSerializable]` (recommended) |
| `JsonBodySerializer(JsonSerializerOptions)` | ❌ | Uses reflection. Already marked with `[RequiresDynamicCode]` |

For AOT, just use the `JsonSerializerContext` constructor in your `ServiceResolver` and declare `[JsonSerializable(typeof(T))]` (see the ServiceResolver sample above).

> HTTP handlers return `APIGatewayHttpApiV2ProxyResponse`, and authorizer handlers return `APIGatewayCustomAuthorizerV2SimpleResponse` / `APIGatewayCustomAuthorizerV2IamResponse`. These are serialized by the Lambda runtime serializer. For AOT, make sure your Lambda serializer's `JsonSerializerContext` also covers those response types (in addition to your DTOs).

## Native AOT Entry Point

A Native AOT function runs on the custom runtime (`provided.al2023`) as an executable named `bootstrap`, so the program needs a `Main` that starts the Lambda runtime client.
Add `[assembly: LambdaEntryPoint]`, and the Source Generator generates `Main` for all handlers in the assembly.

```csharp
[assembly: LambdaEntryPoint]
[assembly: LambdaSerializer(typeof(SourceGeneratorLambdaJsonSerializer<AppJsonContext>))]
```

```xml
<PropertyGroup>
  <OutputType>Exe</OutputType>
  <PublishAot>true</PublishAot>
</PropertyGroup>

<ItemGroup>
  <PackageReference Include="Amazon.Lambda.RuntimeSupport" Version="x.x.x" />
</ItemGroup>
```

- `Main` selects the handler by the `_HANDLER` environment variable, which holds the handler setting of the function. The name is the same as the one for the managed runtime (`{Assembly}::{Namespace}.{ClassName}::{Method}_Handler`), so the infrastructure definition does not need another name for Native AOT.
- If `_HANDLER` matches no handler, `Main` throws `InvalidOperationException` at startup.
- The Lambda runtime serializer is created from the assembly-level `[LambdaSerializer]`. Its `JsonSerializerContext` must cover the request and response types of every handler (for example, `APIGatewayHttpApiV2ProxyRequest` / `APIGatewayHttpApiV2ProxyResponse`).
- Do not declare another `Main` or top-level statements in the project.

## Scope / Non-goals

This library only generates wrapper code (Source Generator output). The following are intentionally out of scope.

- **API Gateway HTTP API (V2) only** — REST API (V1) / `[RestApi]` / `[RestApiAuthorizer]`, and the HTTP API V1 payload are not supported.
- **No config file generation** — It does not generate or sync `serverless.template` / CloudFormation / SAM. `[FunctionUrl]` is a marker attribute only (auth/CORS settings such as `AuthType` are configured on the SAM / CDK side), and `Authorizer = nameof(...)` is used only for diagnostics, not for emitting infrastructure definitions.
- **No method-level infrastructure settings** — Settings such as `Timeout` / `MemorySize` / `Role` / `Policies` / `PackageType` (equivalent to `[LambdaFunction]`) should be configured on the SAM / CDK side.
